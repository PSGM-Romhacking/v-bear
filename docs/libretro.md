# V-Bear as a RetroArch core (libretro)

**English** · [Português](libretro.pt-BR.md) · [Español](libretro.es.md)

V-Bear also ships as a `v_bear_libretro` core (`.so` on Linux and FreeBSD, `.dll` on
Windows) that runs inside RetroArch. RetroArch then takes care of window, video, shaders,
audio, controls, remapping, save states, rewind, run-ahead, netplay and RetroAchievements.

What was tested:

- **Windows:** run by hand in RetroArch. The core loads, the BIOS is found in `system/supracan/`, and
  `.bin`, `.can`, `.zip` and `.7z` games open from the content loader.
- **Linux:** the `.so` was driven by a program that
  plays RetroArch's part through the C API (BIOS lookup, `retro_run`, a ~267 KB save-state round trip, the 32 KB
  battery RAM). The same program checks that the BIOS is found in
  `system/supracan/`, `system/superacan/` and `system/SuperAcan/`, loose, in a `.zip` and in a `.7z`, and that
  Super Dragon Force (two parts, in a `.zip` or `.7z`) loads and shows the same picture as the joined file.
- **FreeBSD and macOS:** the FreeBSD core is built by the release pipeline; there is no macOS release.
- The picture, the sound and the frame rate were not compared between the core and the standalone app;
  the core reports the same 320 × 240 picture, 4:3 aspect and 59.92 fps as the app (`INFO`).

## What a libretro core is

A dynamic library that exports C functions with fixed names (`retro_*`). RetroArch loads
it, hands over the ROM and calls `retro_run()` once per frame; the core returns the frame
and the audio, and reads the buttons through *callbacks* registered beforehand. The core
does **not** open a window, play sound, read the keyboard or create threads: it only
emulates. Reference: `libretro.h` at
<https://github.com/libretro/libretro-common/blob/master/include/libretro.h> and
<https://docs.libretro.com/development/cores/developing-cores/>.

## How it is built here

`crates/v-bear-libretro` (`crate-type = ["cdylib"]`) wraps `v-bear-core` through the
`emu_api::Core` trait; it uses neither egui nor `emu-frontend`. It is generated by
`tools/new-emulator.sh --libretro` from `tools/templates/libretro.rs.in` and has nothing
system-specific in it: everything comes from `SystemInfo` and the trait. The interface and
the libretro core use **the same** core crate, so an emulation fix applies to both.

| libretro | Taken from |
|---|---|
| `retro_get_system_info` | `SystemInfo::name`, `extensions`; `need_fullpath = false`, `block_extract = false` (RetroArch unpacks `.zip`/`.7z`) |
| `retro_get_system_av_info` | the current frame's geometry, `Core::fps()`, audio at 48000 Hz |
| `retro_load_game` | `SystemInfo::create(48000)` + `Core::load`; pixel format XRGB8888 |
| `retro_run` | input poll → RetroPad bitmask per player → `Core::run_frame` → video and audio (f32 → i16) |
| `retro_serialize*` | `Core::save_state` / `load_state` |
| `retro_get_memory_*` | `RETRO_MEMORY_SYSTEM_RAM` → `Core::system_ram` (cheats and RetroAchievements) |
| core options | `Core::options()` / `set_option()`, as `v_bear_<key>` variables ("label; value\|value", the first value is the default) |
| input descriptors | `SystemInfo::buttons` (only the buttons the system has, with their names) |

The API has no context pointer, so the core lives in a global, and every exported function
catches panics: none may cross into C.

**Options:** none (`Core::options()` is empty). **What differs from the standalone app:**

- **Games in two files** (Super Dragon Force, two mask ROMs): the core asks RetroArch for the *path*
  (`need_fullpath` and `block_extract`), because RetroArch would unpack only one file of an archive, and
  reads the `.zip`, the `.7z` or the loose file itself, joining all the files, largest first, as the standalone
  app does. A `.7z` or `.zip` with the two chips works as it is.
- **BIOS:** the core looks for the four files in RetroArch's `system/supracan/` folder first (the main
  one), then in `system/superacan/` and `system/SuperAcan/` (the MiSTer's spelling), then in `system/`, loose or
  inside `.zip` or `.7z` files, and recognizes them by CRC32 under any name. The standalone app
  also reads the BIOS folder chosen in its menu.
- **RetroArch's own cheats:** `retro_cheat_set` does nothing. The work RAM is exposed
  (`retro_get_memory_data`), which is what the cheat search and RetroAchievements read; the
  standalone app's `.cht` cheats are not read by the core.
- Filters, shaders and the frame around the picture belong to RetroArch.

## Save states, rewind and determinism

RetroArch also uses `retro_serialize` for **rewind, run-ahead and netplay**: the core gets
them for free if the state is **complete, deterministic and of fixed size**. Any new state
field in the core must go into the snapshot, and the test "save → run → restore → run gives
the same picture and RAM" must keep passing.

**The size must never grow** while a game is loaded (libretro's rule: RetroArch asks once and sizes its
rewind buffer from the answer). V-Bear's real state is about 267 KB and varies by about 150 bytes from one frame to
the next (the CPU is saved as text), so the core always reports 272 KiB and pads the state with zeros; a state
larger than that is refused. The largest measured, over the 12 games and 4,000 frames each, is 267,322 bytes.

## The `.info` file

RetroArch needs `v_bear_libretro.info` next to the core (or in its info folder) to list it
nicely.

The V-Bear one (`crates/v-bear-libretro/v_bear_libretro.info`) has `display_name = "Funtech - Super A'Can
(V-Bear)"`, `manufacturer = "Funtech"`, `systemname = "Super A'Can"`, `systemid = "super_acan"`,
`database = "Funtech - Super Acan"` (the name of the No-Intro set copied in libretro-database),
`supported_extensions = "bin|can|zip|7z"`, `license = "GPLv3"`, `needs_fullpath = "true"` (the core reads the file itself),
`database_match_archive_member = "true"` (the playlist keeps the `.zip` or `.7z`, which Super Dragon Force needs),
`savestate = "true"`, `savestate_features = "serialized"` (with `"basic"` RetroArch refuses to rewind), `cheats = "false"` and `core_options = "false"`, a short `description`, and lists the four
BIOS files as `firmware0` to `firmware3`, with `supracan/<file>` paths. Whether RetroArch's content scanner
recognizes the games through that database was not tested.

Two things that cost time: RetroArch **caches the core information**, so after copying a new `.info` the
core can keep showing as `v_bear_libretro` with no description and the file browser keeps hiding `.bin`
and `.can` files; clear RetroArch's core information cache and reopen it.
The `.info` goes in RetroArch's `info/` folder.

## Sending the core to libretro

To get the core into RetroArch's Core Downloader, libretro asks for four things
([documentation](https://docs.libretro.com/development/cores/developing-cores/#add-your-core-to-libretro-infrastructure)):

- the `.info` file, sent as a pull request to `libretro-super` (`dist/info/`);
- a `.gitlab-ci.yml` at the root of the repository, which is in this one: it builds only
  `v-bear-libretro` with libretro's Rust templates, for Linux x64 and Windows x64, and renames the
  library to `v_bear_libretro.so` / `.dll`;
- a mirror of the repository on libretro's GitLab, which a maintainer creates on request (Discord, #programming);
- optionally, the core's page in `libretro/docs`.

The CI file has never been run: only libretro's servers can build it. There is no template for FreeBSD,
so that build stays in this repository's release.

## Build and install

```sh
cargo build --release -p v-bear-libretro   # target/release/libv_bear_libretro.so (v_bear_libretro.dll on Windows)
C=~/.config/retroarch/cores                  # or the Flatpak's cores folder
install -m 755 target/release/libv_bear_libretro.so $C/v_bear_libretro.so
install -m 644 crates/v-bear-libretro/v_bear_libretro.info $C/
retroarch -L $C/v_bear_libretro.so "game.bin"
```

The core must not depend on libraries the RetroArch runtime lacks (the Flatpak, for
example): that is one more reason to keep the core crate free of egui, cpal, files and the
clock.

## Testing

- The generated crate has a test that runs the C API against the core used directly and
  compares frames and a save state round trip; give it a ROM with
  `V_BEAR_TEST_ROM=/path/game cargo test -p v-bear-libretro`.
- The base's host (`libretro-host`) loads any libretro core as an `emu_api::Core`:
  `LIBRETRO_TEST_CORE=/path/core.so cargo test -p libretro-host --test real_core`.
- Compare frames: the same game in the standalone app and in the core must produce the
  same picture.

## What is missing

- RetroArch's cheat codes (`retro_cheat_set`).
- `SET_MEMORY_MAPS`: not used, so RetroAchievements cannot map addresses by region.
- No core options.

## RetroAchievements

Not investigated: whether RetroAchievements accepts the Super A'Can was not checked. The core already
exposes the 64 KB of work RAM (seen from `$FC0000` by the 68000), but without `SET_MEMORY_MAPS`.
