## What a libretro core is

A dynamic library that exports C functions with fixed names (`retro_*`). RetroArch loads
it, hands over the ROM and calls `retro_run()` once per frame; the core returns the frame
and the audio, and reads the buttons through *callbacks* registered beforehand. The core
does **not** open a window, play sound, read the keyboard or create threads: it only
emulates. Reference: `libretro.h` at
<https://github.com/libretro/libretro-common/blob/master/include/libretro.h> and
<https://docs.libretro.com/development/cores/developing-cores/>.

## How it is built here

`crates/{{SLUG}}-libretro` (`crate-type = ["cdylib"]`) wraps `{{CORE_CRATE}}` through the
`emu_api::Core` trait; it uses neither egui nor `emu-frontend`. It is generated by
`tools/new-emulator.sh --libretro` from `tools/templates/libretro.rs.in` and has nothing
system-specific in it: everything comes from `SystemInfo` and the trait. The interface and
the libretro core use **the same** core crate, so an emulation fix applies to both.

| libretro | Taken from |
|---|---|
| `retro_get_system_info` | `SystemInfo::name`, `extensions`; `need_fullpath = false`, `block_extract = false` (RetroArch unpacks `.zip`/`.7z`) |
| `retro_get_system_av_info` | the current frame's geometry, `Core::fps()`, audio at 48000 Hz |
| `retro_load_game` | `SystemInfo::create(48000)` + `Core::load`; pixel format XRGB8888 |
| `retro_run` | input poll → RetroPad bitmask per player → `Core::run_frame` → video and audio (f32 → i16) |
| `retro_serialize*` | `Core::save_state` / `load_state` |
| `retro_get_memory_*` | `RETRO_MEMORY_SYSTEM_RAM` → `Core::system_ram` (cheats and RetroAchievements) |
| core options | `Core::options()` / `set_option()`, as `{{ID}}_<key>` variables ("label; value\|value", the first value is the default) |
| input descriptors | `SystemInfo::buttons` (only the buttons the system has, with their names) |

The API has no context pointer, so the core lives in a global, and every exported function
catches panics: none may cross into C.

## Save states, rewind and determinism

RetroArch also uses `retro_serialize` for **rewind, run-ahead and netplay**: the core gets
them for free if the state is **complete, deterministic and of fixed size**. Any new state
field in the core must go into the snapshot, and the test "save → run → restore → run gives
the same picture and RAM" must keep passing.

## Build and install

```sh
cargo build --release -p {{SLUG}}-libretro   # target/release/lib{{ID}}_libretro.so
C=~/.config/retroarch/cores                  # or the Flatpak's cores folder
install -m 755 target/release/lib{{ID}}_libretro.so $C/{{ID}}_libretro.so
install -m 644 crates/{{SLUG}}-libretro/{{ID}}_libretro.info $C/
retroarch -L $C/{{ID}}_libretro.so "game.{{EXT}}"
```

The core must not depend on libraries the RetroArch runtime lacks (the Flatpak, for
example): that is one more reason to keep the core crate free of egui, cpal, files and the
clock.

## Testing

- The generated crate has a test that runs the C API against the core used directly and
  compares frames and a save state round trip; give it a ROM with
  `{{ID_UPPER}}_TEST_ROM=/path/game cargo test -p {{SLUG}}-libretro`.
- The base's host (`libretro-host`) loads any libretro core as an `emu_api::Core`:
  `LIBRETRO_TEST_CORE=/path/core.so cargo test -p libretro-host --test real_core`.
- Compare frames: the same game in the standalone app and in the core must produce the
  same picture.
